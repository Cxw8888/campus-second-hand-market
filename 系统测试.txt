X.5.3 结果分析
这一分布同时验证了三个核心机制：

① CAS 防超卖（200 恰好 1 个）
UPDATE tb_product SET stock = stock - N, status = ... WHERE id = ? AND stock >= N AND status = 1 的原子性保证了 1000 个并发请求中恰好只有 1 个成功扣减。

② 售罄状态联动（204 占 99%）
抢购成功后，商品 status 从 1（上架）联动改为 2（售罄）。后续 990 个线程在商品可见性校验阶段即被拦截，返回 204。这一机制将大部分并发压力在早期拦截，减少了无效的 CAS 尝试，是性能优化的关键。

③ 防重 Token 隔离（202 出现 0 次）
每个线程独立获取 Token，所以没有请求因为 Token 冲突被拦，验证了"防重 Token 按用户 UUID 隔离"的设计。

X.5.4 与修复前的对比

状态联动（售罄标记） 生效

X.6 缺陷发现与修复
本章测试过程中共发现并修复了 5 个代码级缺陷，其中 2 个是仅在运行时才暴露的"隐蔽 Bug"。

X.6.1 缺陷一：Jackson 无法序列化 LocalDateTime
现象：接口 /admin/audit-log/list 返回 500 服务器内部错误。

根因：JacksonConfig.java 第 23 行调用了 builder.modules(module)。该方法会同时关闭 findModulesViaServiceLoader 和 findWellKnownModules 两条自动注册通道，导致 JavaTimeModule 被静默屏蔽。报错信息中提示的 "add Module jackson-datatype-jsr310" 是误导性的——依赖早就在 classpath 上。

验证方式：用 javap 反编译 Jackson2ObjectMapperBuilder 的字节码，确认 modules(...) 会将 findWellKnownModules 置为 false。

修复：改用 builder.modulesToInstall(module)，仅添加自定义模块，不关闭自动注册。

X.6.2 缺陷二：MySQL SET 子句赋值顺序
现象：商品在库存未归零时被误置为售罄，导致后续下单返回 204。

根因：ProductMapper.deductStock 的 SQL：

sql
UPDATE tb_product SET stock = stock - #{quantity},
    status = CASE WHEN stock - #{quantity} = 0 THEN 2 ELSE status END
MySQL 的 UPDATE 赋值从左到右求值，status 的 CASE 表达式读到的 stock 已经是扣减后的新值。因此条件实际变成了"新库存 - quantity == 0"，即"旧库存 == 2 × quantity"时才置售罄。

验证方式：用临时表在真实 MySQL 8.0.46 上对拍 5 组场景，证明修复前后行为差异。

修复：将 status 赋值移到 stock 之前：

sql
UPDATE tb_product SET status = CASE WHEN stock - #{quantity} = 0 THEN 2 ELSE status END,
    stock = stock - #{quantity} WHERE ...
此时 CASE 读到的 stock 是扣减前的旧值，语义正确。

影响面：这个 Bug 是双向的——既会在 stock=2, qty=1 时误判售罄，也会在 stock=1, qty=1 时漏判售罄。

X.6.3 缺陷三：AI 检索参数名不匹配
现象：GET /api/v1/ai/search?query=教材 返回全部上架商品，而非关键词过滤结果。

根因：AiSearchController 的形参是 @Valid ProductQuery query，但 ProductQuery 类中并没有 query 字段，只有 keyword 字段。Spring 会静默忽略未知的 ?query= 参数，导致 LIKE 过滤条件不生效。

修复：Controller 显式接收 @RequestParam("query") 并映射到 ProductQuery.keyword，同时新增负向对照用例（?query=ZZZ不存在 应返回 total=0）防止回归。

X.6.4 缺陷四：幂等响应消息被静默丢弃
现象：重复支付订单时返回 {"code":200, "msg":"操作成功"}，而文档要求返回 "请勿重复操作"。

根因：OrderServiceImpl 有两条幂等路径。SQL 之后的路径走 throw BusinessException(SUCCESS, "请勿重复操作")，消息能进响应体；而 SQL 之前的快捷预检走 return idempotentResult(order, msg)，返回值类型是 OrderVO，承载不了提示文案。

修复：统一 8 处预检路径改为 throw BusinessException(SUCCESS, "请勿重复操作")，删除死代码 idempotentResult。

X.6.5 缺陷五：401 响应语义不一致
现象：登出后 Token 失效返回"请先登录"，改密后 Token 失效返回"登录已失效，请重新登录"。两者都是正确的 401，但语义混淆。

根因：resolveClaims() 把"未携带凭证"和"携带但不可用"两类情况塌缩成同一个 null，信息在那一层丢失。更严重的是，JWT 2 小时过期后也返回"请先登录"——但用户明明是"登录过、只是过期了"，这是最常见的真实场景。

修复：在 preHandle 中独立判断 hasCredential，让"是否携带"和"是否有效"成为两个正交维度，一次覆盖登出、过期、篡改、改密、封禁等 5 类场景。

四、本批踩到的坑（验证工具，不是产品缺陷 —— 差点误判 M5 修复无效）
	现象	场景 d 首次实测返回"编辑后 status=1"（期望 3），看起来像 M5 修复没生效
	根因	Windows PowerShell 5.1 的 Invoke-RestMethod -Body <string> 默认按 ISO-8859-1 编码请求体，
		中文全部变成 '?'：`v605-D-售罄改标题` 与 `v605-D-改过的标题` 编码后字节完全相同（末尾 6 字节都是 45,63,63,63,63,63），
		服务端收到的两个标题一模一样 → 关键字段变更=false → 走"仅补库存"分支回 1
	定位方式	读服务端日志「商品编辑成功: id=…, status=2→1, 关键字段变更=false」，再用 .NET 编码实测两串中文的编码结果对比
	修正	脚本改为显式 UTF-8 字节 + charset=utf-8 后重跑，场景 d 通过（2→3, 关键字段变更=true）
	沉淀	已写入 PROJECT_CONTEXT 3.9.6（连同"脚本文件需带 BOM 的 UTF-8""按钮断言不要用整页 text() 判断"两条同类约定）
