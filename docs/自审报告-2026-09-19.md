## 一、必须立刻修（Blocker）

### S1. JWT 默认密钥 + prod 不强制注入 ⇒ 默认配置下任何人可伪造管理员 Token ✅

- **证据**
  - `src/main/resources/application.yml:122`
    `secret: ${JWT_SECRET:campus-market-dev-secret-key-please-override-in-env-32bytes}`
  - `src/main/java/com/campus/market/util/JwtUtils.java:38-44`：**只校验长度 ≥ 32 字节**（默认值 59 字节，校验通过）
  - `src/main/resources/application-prod.yml`：全文**没有** `app.jwt` 段（只强制了 `DB_*` 与 `CORS_ALLOWED_ORIGINS`）
- **触发**：部署时漏设 `JWT_SECRET`（prod 缺变量**不会**启动失败）。由于仓库为 Public，该默认密钥已公开；攻击者用自己账号登录后读出自己 Token 里的 `version`，用公开密钥重签 `{"userId":自己,"role":1,"version":同值}` → 通过验签 + version 比对 + 用户状态校验 → 管理端全通。
- **影响**：完全越权（管理员功能），且可伪造任意 `userId` 冒充他人。
- **修复方向**：prod profile 写死 `app.jwt.secret: ${JWT_SECRET}`（无默认值，缺失即启动失败）；启动时拒绝"与 dev 默认值相同"的密钥；轮换密钥使旧 Token 全部失效。

### S2. `email.skip` 默认 true + 找回密码公开 ⇒ 任意账号密码被重置 ✅

- **证据**
  - `application.yml:15` 默认 profile = dev；`application.yml:148` `skip: ${EMAIL_SKIP:true}`
  - `EmailCodeServiceImpl.java:81-86`：skip 模式下 `return new EmailCodeVO(true, code, expireSeconds)`（**验证码进响应体**）
  - `GET /api/v1/auth/email-code` 与 `POST /api/v1/auth/reset-password` 均在公开路径（`PathConstants.java:50-54`），`AuthServiceImpl.java:209-234` 的 reset 只校验"邮箱 + 验证码"
- **触发**：知道受害者的校园邮箱（学号@stu.edu.cn，可推测）→ 请求验证码（响应里就有）→ 提交 reset-password → 拿到账号控制权。
- **影响**：任意账号接管（无前置条件）。这是**有意的答辩降级设计**，但"默认 profile + 默认 skip"的组合使"忘设环境变量"直接等于"账号可被接管"。
- **修复方向**：`EMAIL_SKIP` 默认改 false；生产 fail-fast 断言 `skip == false` 且 profile 非 dev；任何情况下响应体不回显验证码（dev 除外，见 6.0.1）。

### S3. 支付回调公开且**完全没有签名校验**（代码与文档相反）✅

- **证据**
  - `OrderController.java:76-81` 的 `@Operation(description = "公开路径（**签名校验**）")`
  - 但 `PayCallbackRequest.java` 只有 `orderNo` + `tradeNo`（**无 sign / 时间戳 / 金额**）
  - `OrderServiceImpl.java:157-191` 只做 Redis 去重 + 状态机，直接 `orderMapper.pay(id)`（0→1）
  - 该路径在 `OPTIONAL_AUTH_PATHS`（`PathConstants.java:54`）且被 `WebMvcConfig` 排除在拦截器之外；**前端从不调用它**（前端走认证的 `PUT /order/pay/{id}`）
- **触发**：`curl -X POST /api/v1/order/pay/callback -d '{"orderNo":"<已知待支付订单号>","tradeNo":"任意"}'` → 订单变"已支付"，卖家收到「买家已支付，请尽快发货」站内信。
- **影响**：买家可自助跳过支付（面交场景下卖家据此发货）；对他人订单，知道 orderNo 即可远程触发假"已付款"通知。
- **修复方向**：回调改为服务端共享密钥签名（或强制认证 + 归属校验 + 金额校验）；失败一律拒绝且不改状态；把注释与实现统一。

### B1. 封禁 + 解冻的**双重库存回补**，以及 5→3 完成**不回扣** ⇒ 库存失真 / 超卖 ✅

- **证据**
  - `AdminServiceImpl.java:193-200`（封禁）：`freezeByUser(userId)` 冻结 0/1/2/6 → 然后**逐单 `stockService.restore(...)`**
  - `AdminServiceImpl.java:256-262`（解冻 CANCEL）：`unfreezeToCancel(id)` 5→4 后又 **`stockService.restore(...)`**
  - `AdminServiceImpl.java:266-275`（解冻 COMPLETE）：`unfreezeToComplete(id)` 5→3，**没有任何扣减**
  - `ProductMapper.java:141-143` `restoreStock` 无"是否已回补"标记，任何重复调用都真实加库存
- **触发与后果**
  1. 库存 1 的商品下单（库存 0）→ 封禁卖家（库存回到 1）→ 管理员解冻选 **CANCEL**（库存变 **2**）= 一单刷两次库存；
  2. 封禁（库存已回补）→ 解冻选 **COMPLETE**（订单=已完成，货已交付）→ 商品库存却多 1 件且仍在售 = **真实超卖**；
  3. 反复"封禁 → 解冻"可无限刷库存。
- **修复方向**：冻结与解冻**只能有一处**负责回补（建议：封禁不回补，只在 5→4 回补）；5→3 前必须 CAS 扣减库存；给回补加幂等凭证（订单维度的 `restored` 标记或唯一约束）。

### B2. 封禁顺序 + `restoreStock` 的 CASE ⇒ 被封禁卖家的**售罄商品重新上架** ✅

- **证据**
  - `AdminServiceImpl.java:181-190` 下架只命中 `status=1`（`eq(status, ON_SALE)`），售罄商品是 `status=2`，不在下架范围
  - 紧接着 `:197-199` 的回补 SQL：`SET stock = stock + q, status = CASE WHEN status = 2 THEN 1 ELSE status END`（`ProductMapper.java:141-143`）把**售罄翻回上架**
  - `OrderCreateService.java:49-55` 下单**只校验商品 status=1，不校验卖家是否被封禁**
- **触发**：库存 1 商品被下单 → 售罄(2) → 封禁卖家 → 商品回到 status=1 → 其他买家继续下单，**封禁形同虚设**。
- **修复方向**：调整顺序（先冻结/回补再下架）且回补不得把 2 改回 1；下单时一并校验卖家 `status`。

## 三、次要问题（Minor / Info）

### 交易与库存

1. `UNFINISHED_ORDER_STATUS` 缺 5（冻结，`ProductServiceImpl.java:156-163`）→ 冻结订单的商品可被删除，之后解冻取消时 `restoreStock` 因 `AND is_deleted = 0` 命中 0 行，库存静默丢失。
2. 冻结集合缺 7（`OrderMapper.java:87`）→ 被封禁用户"退款被拒"的单 3 天后仍会自动恢复 1/2 继续流转。
3. 超时取消不区分 `trade_type`（`OrderMapper.java:117-118`）→ **面交单 15 分钟即被自动取消**（校园约见面常超过 15 分钟）。
4. `trade_type=3`（皆可）订单走不了面交终态（面交三处 SQL 都要求 `trade_type=1`）→ 当面交易被迫点"发货"，与"面交不该出现已发货"的设计冲突。**根因**：下单页让买家选了面交/邮寄（`OrderCreateView.vue:124`），但**选择没有传给后端**，订单快照取的是商品维度。
5. `quantity` 只有 `@Min(1)` 无 `@Max`（`OrderCreateRequest.java:27-30`；CAS 兜住不超卖，仅缺边界校验）。
6. `resolveStatus` 非售罄分支不看新库存（`ProductServiceImpl.java:753-761`）→ 卖家把库存改成 0 后 status 仍是 1（列表可见却买不到，下单返 201）。
7. 并发下幂等码不稳定（`OrderServiceImpl.java:371-379` 用 SQL **之前**读到的状态判定）→ 双击可能得到 209 而非约定的 200「请勿重复操作」。
8. 防重 Token 无 Redis 降级（`OrderTokenService.java:55-63`）→ Redis 故障时**全站无法下单并抛 500**（fail-closed 可接受，但应给友好错误）。
9. 回调去重键写在事务内（`OrderServiceImpl.java:159-166`）→ 事务回滚后键已占位，同一笔流水重试会被永久吞掉。
