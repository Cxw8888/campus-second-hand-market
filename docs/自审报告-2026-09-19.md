## 一、必须立刻修（Blocker）

### S1. JWT 默认密钥 + prod 不强制注入 ⇒ 默认配置下任何人可伪造管理员 Token ✅ —— **已修复（6.0.1）**

- **证据**
  - `src/main/resources/application.yml:122`
    `secret: ${JWT_SECRET:campus-market-dev-secret-key-please-override-in-env-32bytes}`
  - `src/main/java/com/campus/market/util/JwtUtils.java:38-44`：**只校验长度 ≥ 32 字节**（默认值 59 字节，校验通过）
  - `src/main/resources/application-prod.yml`：全文**没有** `app.jwt` 段（只强制了 `DB_*` 与 `CORS_ALLOWED_ORIGINS`）
- **触发**：部署时漏设 `JWT_SECRET`（prod 缺变量**不会**启动失败）。由于仓库为 Public，该默认密钥已公开；攻击者用自己账号登录后读出自己 Token 里的 `version`，用公开密钥重签 `{"userId":自己,"role":1,"version":同值}` → 通过验签 + version 比对 + 用户状态校验 → 管理端全通。
- **影响**：完全越权（管理员功能），且可伪造任意 `userId` 冒充他人。
- **修复方向**：prod profile 写死 `app.jwt.secret: ${JWT_SECRET}`（无默认值，缺失即启动失败）；启动时拒绝"与 dev 默认值相同"的密钥；轮换密钥使旧 Token 全部失效。

### S3. 支付回调公开且**完全没有签名校验**（代码与文档相反）✅ —— **已修复（6.0.2）**

> 6.0.2 实施：引入 HMAC-SHA256 共享密钥验签（时间戳窗口 → 签名非空 → 常量时间比对 → 订单存在，
> 任一失败 code=100「回调签名校验失败」且不改状态；未配置密钥时 fail-closed），`@Operation` 注释同时改成名副其实。
> **遗留缺口**：签名不含金额（`PayCallbackRequest` 无 amount 字段），见 §8。

- **证据**
  - `OrderController.java:76-81` 的 `@Operation(description = "公开路径（**签名校验**）")`
  - 但 `PayCallbackRequest.java` 只有 `orderNo` + `tradeNo`（**无 sign / 时间戳 / 金额**）
  - `OrderServiceImpl.java:157-191` 只做 Redis 去重 + 状态机，直接 `orderMapper.pay(id)`（0→1）
  - 该路径在 `OPTIONAL_AUTH_PATHS`（`PathConstants.java:54`）且被 `WebMvcConfig` 排除在拦截器之外；**前端从不调用它**（前端走认证的 `PUT /order/pay/{id}`）

### B1. 封禁 + 解冻的**双重库存回补**，以及 5→3 完成**不回扣** ⇒ 库存失真 / 超卖 ✅ —— **已修复（6.0.3）**

- **证据**
  - `AdminServiceImpl.java:193-200`（封禁）：`freezeByUser(userId)` 冻结 0/1/2/6 → 然后**逐单 `stockService.restore(...)`**
  - `AdminServiceImpl.java:256-262`（解冻 CANCEL）：`unfreezeToCancel(id)` 5→4 后又 **`stockService.restore(...)`**
  - `AdminServiceImpl.java:266-275`（解冻 COMPLETE）：`unfreezeToComplete(id)` 5→3，**没有任何扣减**
  - `ProductMapper.java:141-143` `restoreStock` 无"是否已回补"标记，任何重复调用都真实加库存
- **触发与后果**
  1. 库存 1 的商品下单（库存 0）→ 封禁卖家（库存回到 1）→ 管理员解冻选 **CANCEL**（库存变 **2**）= 一单刷两次库存；
  2. 封禁（库存已回补）→ 解冻选 **COMPLETE**（订单=已完成，货已交付）→ 商品库存却多 1 件且仍在售 = **真实超卖**；
  3. 反复"封禁 → 解冻"可无限刷库存。
- **修复方向**：冻结与解冻**只能有一处**负责回补（建议：封禁不回补，只在 5→4 回补）；5→3 前必须 CAS 扣减库存；给回补加幂等凭证（订单维度的 `restored` 标记或唯一约束）。

> **已修复（6.0.3）**（决策 1 · 方案 A + 决策 2 · Redis 凭证）：
> ① 封禁<b>不再回补</b>，回补只发生在 5→4；② 所有回补统一走 `StockService.restoreOnce(orderId, productId, quantity)`，
> 先抢占 `order:restored:{orderId}`（SETNX，TTL 30 天）再落 SQL；③ 回补未命中 / 抛异常 / **事务回滚**时释放凭证
> （事务回滚用 `TransactionSynchronization.afterCompletion` 钩子，避免"凭证在、库存没加"导致永久少一件库存）；
> ④ Redis 不可用时降级放行（与支付回调去重同一取舍：状态机本身能挡同一条流转重复执行）。
> 真机实测：封禁后库存不变；封禁→解冻 CANCEL 后库存恰好 +1；把订单强行改回 5 再解冻 CANCEL 一次，
> 订单确实再次 5→4 但库存<b>仍为 +1</b>（凭证生效）。

### B2. 封禁顺序 + `restoreStock` 的 CASE ⇒ 被封禁卖家的**售罄商品重新上架** ✅ —— **已修复（6.0.3）**

> **已修复（6.0.3）**（三处一起改）：
> ① `ProductMapper.restoreStock` **移除 `CASE WHEN status = 2 THEN 1`** —— 回补只加库存、不改状态；
> ② 封禁顺序改为「先冻结订单（不回补）→ 再下架商品」，下架条件从 `status = 1` 改为 **`status IN (1,2)`**
> （新增 `ProductMapper.offShelfByUser`，售罄(2) 商品同样下架）；
> ③ `OrderCreateService` 下单时新增**卖家 `status=0` 校验**（失败返回 204「商品不存在或已下架」，
> 不向买家泄露"卖家被封禁"这一他人账号状态）。
> 「交易终止后商品应重新可售」改由**显式的第二步** `ProductMapper.relistIfSoldOut`（`status = 2 AND stock > 0 → 1`，
> 由 `StockService.restoreOnce` 在回补后调用）承担 —— 已下架(0) 的商品不会被它放出来，
> 因此封禁链路（不回补）与解冻取消都不会把被封禁卖家的商品重新上架。
> **一处与任务书的偏差**：任务书 B.a 要求下架覆盖 `status IN (1,2)`，而单测/场景 d 的措辞是"售罄商品保持售罄"；
> 二者不可同时成立（下架即变 0）。本批按 B.a 实现 —— 封禁后售罄商品变为 **0-下架**（不是 1-在售，也不留在 2-售罄），
> 因为 0 才是"管理员下架"的正确语义且同样不可下单。若要求字面保留 2-售罄，把下架条件改回 `status = 1` 一行即可。

- **证据**
  - `AdminServiceImpl.java:181-190` 下架只命中 `status=1`（`eq(status, ON_SALE)`），售罄商品是 `status=2`，不在下架范围
  - 紧接着 `:197-199` 的回补 SQL：`SET stock = stock + q, status = CASE WHEN status = 2 THEN 1 ELSE status END`（`ProductMapper.java:141-143`）把**售罄翻回上架**
  - `OrderCreateService.java:49-55` 下单**只校验商品 status=1，不校验卖家是否被封禁**
- **触发**：库存 1 商品被下单 → 售罄(2) → 封禁卖家 → 商品回到 status=1 → 其他买家继续下单，**封禁形同虚设**。
- **修复方向**：调整顺序（先冻结/回补再下架）且回补不得把 2 改回 1；下单时一并校验卖家 `status`。

### 6.0.4 修复记录

1. **M3（通知的事务边界）**：新增 `TransactionHelper.runAfterCommit(Runnable)`
   （有事务 → 注册 `afterCommit`；无事务 → 立即执行；回调内异常 catch + `log.error` 不冒泡）。
   `NotificationServiceImpl.sendAsync` 改为"先过事务门、再异步派发"，**它自己不再是 `@Async`** ——
   真正的异步抽到独立 Bean `NotificationDispatcher`（`@Async(NOTIFICATION_EXECUTOR)`），
   因为 **Spring 的 `@Async` 同类自调用不走代理**，留在原类会退化成同步执行（请求线程阻塞到重试结束）。
   重试策略（2 次 / 固定 2 秒 / error 降级）保持不变。
   → 事务回滚不再产生"假通知"；CallerRunsPolicy 的 sleep 也因"事务已提交、行锁已释放"而不再阻塞业务行锁。
2. **M4（用户状态缓存）**：`AdminServiceImpl` 的封禁/解封两处 `cacheUserStatus` 改为 `runAfterCommit`；
   `TokenVersionServiceImpl.cacheUserStatus` 写入时带 **TTL 1 天**（修前 `set(key, value)` 无过期）；
   `AuthInterceptor#isUserBanned` 增加读侧兜底 —— 缓存为 `"0"` 直接放行（热路径），
   缓存为 `"1"` 或缺失则**查库并以库为准**，若查出库中正常则删除残留缓存（自愈）。
   → 回滚不再留下"库里正常、缓存封禁"的毒缓存；即使有残留也只影响一次请求且自动修复。
3. **6.0.3 B1 与本批的兼容性（任务 D 的结论）**：Spring 回调顺序固定为

   `AfterCommitAfterCompletionCoexistenceTest`（提交 / 回滚两种结局 + 执行顺序）与真机集成测试覆盖。

1. **S3 遗留：回调未校验金额**（本批决策 4 明确不做）。`PayCallbackRequest` 没有 `amount` 字段，
   签名 payload 只覆盖 `orderNo|tradeNo|timestamp`。模拟支付场景风险可控，
   **接真实网关前必须补**：新增 `amount` 字段并纳入签名，再与 `tb_order.amount` 用 `compareTo` 比对。
2. **M1 的一处主动偏离**：需求原文是"可信代理后取 X-Forwarded-For 的**第一个** IP"，实现改为业界标准的
   "从右往左跳过可信代理、取第一个不可信地址"。原因：nginx 最常见的 `$proxy_add_x_forwarded_for`
   会把客户端自带的 XFF 原样保留并追加，"取第一个"正好取到攻击者可控的那一段，绕过依旧成立。
   单段 XFF（`$remote_addr` 写法）下两种规则结果相同。
3. **M7-a 的实测修正**：仅靠 `knife4j.enable=false` 关不掉 `/doc.html`（它是 knife4j jar 内
   `META-INF/resources/doc.html` 的静态资源），故 prod 另加了文档路径封禁拦截器。
4. **M7-b 未加启动断言**（有意）：Redis 在内网/本机时无口令是正常形态，断言会造成合法部署假失败；
   暴露面应由安全组/绑定地址解决。见 6.0.2 报告「三、技术要点 · M7-b」。
5. **M7 的另一半未做**：仍**无** CSP / X-Frame-Options / X-Content-Type-Options / HSTS 安全响应头
   （本批范围只到"关文档 + Redis 口令"）。列入 6.0.3 建议。
